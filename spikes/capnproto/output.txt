=== Part 3: Schema Evolution ===

Test 1: Forward compatibility — V1 writer, V2 reader
  V1 message: 112 bytes
  timestamp:     1000000 ✓
  serverId:      1 ✓
  schemaVersion: 0 (expected 0 — default for missing field) ✓
  V2 reads V1 bytes without error — missing field defaults to 0.

Test 2: Backward compatibility — V2 writer, V1 reader
  V2 message: 120 bytes
  timestamp: 1000000 ✓
  serverId:  1 ✓
  schemaVersion: (not read — V1 decoder ignores data word 2) ✓
  V1 reads V2 bytes without error — extra data word is silently ignored.

Test 3: Why cereal can't do this (from storage spike)
  Cereal TxNodeV1 + TxNodeV2 have different Serialize instances.
  decode :: Either String TxNodeV2 on V1 bytes = Left (parse error)
  because cereal's get reads exactly the bytes its structure expects.
  Adding a field = breaking change: all existing writers must update.

  Cap'n Proto avoids this because:
    * The struct pointer in every message carries the data section word count.
    * Readers check the actual word count before accessing a field.
    * If a field is beyond the end of the data section: use the default (0).
    * If a field is past what the reader knows about: silently ignored.
  This is exactly the Mnesia property: disk format is versioned by schema,
  not by code. No migration step. No branching decoder.

Size difference: V1=112 bytes, V2=120 bytes (+8 bytes for the new field)

Evolution tests: V1→V2=PASS, V2→V1=PASS
