=== Part 4: Schema Evolution ===

Wrote V1 TxNode (58 bytes)
  Read as V2: FAILED (expected) — too few bytes
From:	demandInput


  cereal verdict: adding a field requires a version byte and branching decoder

Cap'n Proto schema evolution (from schema/datacode.capnp):
  TxNode has fields @0 through @5. Adding @6 is always backward compatible:
    Old writers omit @6 — old bytes on disk are still valid TxNode messages
    New readers see default value for @6 when reading old data
    Old readers ignore @6 entirely — forward compatible too
  This is the Mnesia-like property: the disk format is versioned by the schema,
  not by the data. No migration step, no version byte, no branching decoder.

Summary:
  Append log with length-prefix framing: SUCCEEDED
  Random access by file offset: SUCCEEDED
  Sequential scan: SUCCEEDED
  Encode: 0µs (1.451e-4)/tx
  Decode: 0µs (9.620000000000001e-5)/tx
  Schema evolution: cereal requires version branching; Cap'n Proto is automatic

  Decode: 0µs/tx
  Key findings:
    - Length-prefix framing identical to Cap'n Proto segment framing
    - Random access by LogEntry{offset,length} is O(1) — seek + read
    - cereal encode/decode latency is well within budget at this scale
    - cereal ceiling: schema evolution requires explicit versioning
    - Cap'n Proto eliminates that ceiling: new fields are always backward compatible
    - Cap'n Proto mmap: log bytes on disk = valid Cap'n Proto message in memory
    -   → field access costs only pointer arithmetic, not deserialization
    -   → this is the Mnesia analogy: disk format IS the runtime representation
