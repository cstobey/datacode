# Validation of the two Phase 0 rules

Produced 2026-08-28 by a six-agent pass over the corpus, checking the mandatory-default rule and the
re-key-on-the-transaction-node rule against every `DefaultClause` form, every field declaration in
`docs/`, and the mechanisms both rules touch.

**Both rules survive. Several of the things said *about* them in `00-report.md` did not**, and the
corrections are folded back there. Section (B) is the deliverable that matters most — it is the table
an implementer codes against.

---

# Integration: Rule A (added-column default) and Rule B (re-key on the transaction node)

## (A) Do the rules survive?

**Rule A survives. No objection is fatal.** Five candidate refutations were raised; each is a corpus defect or a scope error, not a break.

- *"Unsatisfiable: a field default is `Tx` and there is no `Sub 'Tx 'Read`"* (`functions.md:39`, `dynamic-loading.md:63-64`, `dynamic-loading.md:69-70`). Dissolves. `functions.md:70` already says the effect is **inferred from the body and checked against the position** — so the `Tx` cell is what the *position* admits, not the index a default carries. Read as a ceiling, the ladder and the rule agree, and the two `Tx` sentences are what must change.
- *"The admissibility criterion is too weak"* — three validations converged independently. Correct, and it is a tightening, not a break: `no write + no ambient input` admits `= (OrderStatus where name == "Pending")` (`railroad.md:490`) and `= other_field * 2`, both of which give an old row a moving value while a row inserted after the add is frozen at insert. The criterion is `Pure` **and** stable for the life of the row.
- *"Too strong for a `:>` field to a `Component` target"* — two validations converged. Correct. Under the table-valued decision (`00-report.md:27-28,41-46`) the old-row value is the empty table, inside the declared type. That field needs no `DefaultClause`; only the constructing `= { theme = Dark }` is rejected. Narrow the rule.
- *"Scoped to table redeclaration, so it misses the trait and generator paths"* — three validations converged. Correct. State it over the **effective field set** and over generators.
- *"`authed_user` fails for the stated reason"* — the stated reason (`00-report.md:408-409`, "there is no requesting token for a row written last year") is **false**. `railroad.md:913` puts `authed_user` in scope in field defaults and every read carries a token, so the default resolves — to whoever is reading. That is worse than failing. The correct reason is that `authed_user` is transaction-ambient input, not row data. Same shape as "time is a parameter, never ambient."

Two citation errors in the decision text: `00-report.md:391` cites `evolution.md:34`, which is the compliant example `table app.commerce.Customer { *, loyalty_tier : Tier = Bronze }`; the contradicting line is `evolution.md:39`. And `00-report.md:407` cites `tables.md:441` for the whole component case when only `:443` (the construction) is affected.

**Rule B survives in substance — the link belongs on the transaction node — but three of its stated claims are false, and one is a defect in the rule as written, not in its consequences.**

- **Fatal to the stated type.** `(old DataId, new DataId)` cannot name a component reparent, and reparenting is precisely what `00-report.md:224` retires `traits.md:220` for. A component has no `DataId` (`traits.md:199`, `transaction-graph.md:475-476`) and its identifier is variable-length (`transaction-graph.md:493`). Two validations converged. Type the fields as the `head_index` row key (`storage.md:43-45`) — `DataId`, or `DataId` plus one `Ordinal` per level — which is the key the index is already keyed by.
- **"Queryable" is false.** No `system.` table exposes transaction nodes; `TxnCmd` (`railroad.md:818-819`) is CLI-only. `system.integrity.Violation` is queryable because it is an ordinary table (`integrity.md:299-302`) — the property belongs to the alternative Rule B rejected. Either declare `system.graph.Transaction` or strike the word.
- **"Costs nothing per row" understates, and the evidence is for the wrong field kind.** A `List(struct)` is a *pointer* field: one pointer word on every `TxNode` in the cluster forever. `spikes/capnproto/output.txt:89-95` measured a data-section scalar (`schemaVersion @6 :UInt32`, `datacode.capnp:53`) and explains the mechanism entirely in data-section terms. `storage.md:186-187`'s "exactly 8 bytes per message" is a claim about that scalar. Re-run the spike with a pointer field before leaning on it.
- **The precedent appeal is empty.** Of "a split node, a prune node, and the `erase` and `scrub` records," only scrub has a field list (`integrity.md:413-420`); none appears in the frame at `storage.md:17` or in `datacode.capnp:41-54`, which has no node-kind field at all.
- **`transaction-graph.md:659-661` is miscited** (`00-report.md:418`). That passage objects on **derivability** ("a second source of truth for a derivable fact"), not sparsity. The conclusion holds on a different ground: a supersession is a fact about a transaction, so a row column stores it on the wrong object.
- **The record as specified does not close the gap it was written for.** It is old→new and lives on the coordinator's shard — the *old* one (`distribution.md:412`, B appends nothing on commit). Every consumer starts from the successor: the version-chain walk, `Violation.subject`, `TriggerState.subject`, a queue payload's captured id, merge reconciliation. The record is the right *record*; a server-local, unreplicated new→old index derived from it is what makes it usable.

**Out of scope but adjacent and fatal:** the gate on the parent rule (`00-report.md:246-248`) fails twice. It is stated over "headed by a foreign key reaching the same shard root", which admits a second `unique` headed by a *different* FK whose value the re-key does not change — the gate says yes and the insert collides with its own tombstone (`distribution.md:315-326`). And no `unique` on a root table is headed by an FK reaching a root (that is the *definition* of a root, `tables.md:172`), so the gate rejects every root candidate-key change, with no escape (`distribution.md:325`). Username change, email change, branch rename. See (E).

## (B) The admissible-default table

`DefaultClause ::= '=' ( Expr | SeqAlloc )` (`railroad.md:139-140`), walked through `Atom` (`railroad.md:482-497`). The test is **`Pure`, and stable for the life of the row** — the value must be reproducible at read from the old row plus the schema node, and identical to what an insert after the add would have stored.

| # | `DefaultClause` form | Grammar | Added to an existing table? | Why |
|---|---|---|---|---|
| 1 | `Literal` — `= 0`, `= "Unknown"`, `= True` | `railroad.md:33,482` | **Yes** | Closed, `Pure`, constant-folded at schema commit. The value is a property of the schema node, not of any row. |
| 2 | Nullary variant — `= Bronze`, `= Pending`, `= NotGiven` | `FieldPath`, `railroad.md:483` | **Yes** | Closed constant. Parses as `FieldPath`, not `Literal` (`railroad.md:33` has no variant alternative). The canonical added-`:>` shape is `f :> T \| NotGiven = NotGiven`. |
| 3 | Variant with payload — `= Waived "migrated"` | `FuncApp`, `railroad.md:492` | **Yes, iff** every argument is admissible | Constructor application over admissible arguments is itself closed. |
| 4 | `FuncApp` over a named function — `= defaultTier`, `= percent x 2` | `railroad.md:492` | **Yes, iff** the function's inferred effect is `Pure` and every argument is admissible | Not a new rule: `functions.md:70`'s infer-and-check with `Pure` as the ceiling instead of `Tx`. |
| 5 | `IfExpr`, `LetExpr`, `'(' Expr ')'` | `railroad.md:486-489` | **Yes, iff** every sub-expression is | Structural; carries no effect of its own. |
| 6 | `FieldPath` into an **immutable virtual column** — `= created_at`, `origin_server`, `ordinal`, `grain` | `railroad.md:483` | **Yes** | `tables.md:213-220` already certifies exactly this set as "immutable for the life of the row," for exactly this reason. The one non-literal default in the corpus, `scheduled_at : Timestamp = created_at` (`traits.md:293`), is this form. **Caveat:** immutable for the life of the *`DataId`* — Rule B mints a new one on a re-key. |
| 7 | `FieldPath` into a **stored or mutable** field — `= total * 0.01`, `= updated_at` | `railroad.md:483` | **No** | `Pure` but not stable. A row inserted after the add computes once at insert and stores; an old row computes at read from its current version. Update the source and the two populations diverge, with nothing in the row saying which regime applies. `tables.md:219-220` excludes `updated_at` on precisely this ground. |
| 8 | `= authed_user` | `FieldPath`, `railroad.md:483,913` | **No** | Transaction-ambient input, not row data. It *does* resolve on a read path — to the reader — so `created_by` would differ between two readers of the same row. Fails silently, which is worse than failing. |
| 9 | `Lambda` on a `Behavior`-typed field — `= \t -> …` | `railroad.md:493`, mandatory per `:168-172` | **Yes** — Rule A is vacuous here | The clause is already mandatory and is the *definition*, not a default; nothing is stored (`types.md:113-114`), so old and new rows read identically. This is the mechanism Rule A generalizes. |
| 10 | `FunctorRef` or function literal on a function-typed field — `= renderMoney`, `= \r -> percent r 2` | `railroad.md:483,493`; `functions.md:194-195` | **Yes**, subject to the unchanged trait table at `functions.md:209-213` | The value is a name or a serialized DSL term living in the schema graph; it takes no row input at all. `Reference` admits a literal, `Configuration` a `FunctorRef` only, `Effect` types a name only. |
| 11 | `RecordLit` constructing a `Component` row — `= { theme = Dark }` | `railroad.md:488,496`; `tables.md:437-443` | **No — and no default is needed** | The construction inserts a row in the same transaction; there is no transaction for a row committed last year. But the field is table-valued (`00-report.md:27-28`), so its old-row value is the **empty table** — inside the declared type, no write, no ambient input. **Add the field with no `DefaultClause` at all.** |
| 12 | `RecordLit` on a `:>` to a **non-`Component`** table — `owner :> User = { name = "x" }` | `railroad.md:488` | **No** | The grammar admits it and nothing gives it a meaning; `railroad.md:182-185` makes the *sub-table body* what constructs, so this constructs nothing. If it did construct, it is the cross-table in-commit write `events.md:480-484` refuses. Reject; see (E) for which rejection is normative. |
| 13 | `'(' Query ')'` atom, or `Expr '$' Query` | `railroad.md:468,490` | **No** | `Read`, not `Pure`. No ambient input — the sample moment is a parameter, not a clock (`queries.md:390-402`) — but the old row's value moves with each reader's moment while a post-add insert is frozen. `queries.md:409`: "Stored rows make the moment immaterial." A default that varies per observation is a `Behavior` with the `Moment` hidden; row 9 is the honest spelling. |
| 14 | `SeqAlloc` — `= next orderRef` | `railroad.md:140,178-181`; `tables.md:232-258` | **No** | It allocates, not evaluates: a read-modify-write on a counter row (`tables.md:258,276-278`). Genuinely `Tx`, and the only reason the ladder's `Tx` cell exists for defaults at all. |
| 15 | **No `DefaultClause`** | — | **No, except** rows 9 and 11 | Row 9 already carries a mandatory clause that `railroad.md:168-172` says is not a default; row 11 has a well-typed empty value. Everything else is a compile-time error. |

Two rules follow from the table and should be stated with it: the default must **satisfy the field's own `WhereClause`** (under Rule A it becomes the value of every existing row, so a default failing its own predicate marks 100% in one commit — a schema error, not a migration choice); and **no `unique` field can be added to a populated table**, because every admissible default is constant, `next` is row 14, and no injective row-local expression is spellable (`id` does not exist, `00-report.md:670`; the `DataId` counter is not exposed, `tables.md:31`).

## (C) Consequences to write down

### Rule A

| Consequence | Normative home | Why |
|---|---|---|
| The `Tx` cell in the effect ladder is a **position ceiling**, not the index a default carries; the body's inferred effect is what the field holds, and an added field's must be `Pure`. | `schema/functions.md#the-effect-ladder`; `dynamic-loading.md:62-65` links out instead of restating | `functions.md:70` already says infer-and-check; two copies of the claim is the drift defect. |
| Rule A is a property of the **commit diff**, not of the body text: restating a field in a `*` body is not adding it and needs no default. | `schema/evolution.md#redeclare-a-table` | Every "change a validation" example in `evolution.md` restates a pre-existing field with no default. |
| The predicate is not "carries a `DefaultClause`" but "carries a default that infers `Pure` and is stable for the life of the row." One rule, not two that appear to disagree. | `schema/railroad.md` `FieldDecl` constraint list; rationale in `evolution.md` | `= next`, `= { … }`, `= authed_user` all satisfy the syntactic rule and are then rejected by a second one. |
| A `:>` field to a `Component` target may be added to a populated table with **no** `DefaultClause`. | `schema/tables.md#a-component-default-constructs-the-row` | Empty table is a value inside the declared type; symmetric with the `Behavior` case. |
| A `Behavior` field satisfies Rule A by construction and is the model for it — computed at read, never stored, identical on both populations. | `schema/types.md#behaviors`, one clause on `railroad.md:168-172` | Prevents a reader concluding a `Behavior` needs a second `=`, or acquires default semantics. |
| Rule A binds the **effective field set** — body fields plus inherited ones — and is checked twice on the trait path: at the trait (a field added to an existing trait must carry a default, because the set of extending tables grows after the commit and "does the table have rows" is undecidable) and at the table gaining a trait (whose fields may predate the rule). | `schema/traits.md`, new section; bullets in `railroad.md`'s `TraitItem` list and `evolution.md:42` | 13 of 22 trait fields in the corpus carry no default, so those traits are unaddable to any populated table and nothing says so. This is a **stronger** argument for the unconditional polarity than the dev/prod one at `00-report.md:384-388`. |
| A table may discharge Rule A for an inherited trait field by **bare redeclaration supplying a default**, for that table only. | `schema/traits.md#multiple-inheritance`, extending `:68-88` | The grammar already permits it; only the semantics is missing. It is the sole site with the knowledge. |
| Rule A binds **generators**, not just authors: the connector shadow schema, `Doc indexed` siblings, rollup levels, and a split's generated `:>`. The connector's default is read off the source DDL (`DEFAULT` if present, else `\| NotGiven = NotGiven`, else the implicit value the source itself backfilled) — never an exemption for shadow namespaces. | `connectors.md#schema-auto-discovery`; one line in `evolution.md` naming the four | `connectors.md:171` makes automated column addition designed behaviour; a refused commit stalls the binlog. A default chosen for tidiness rather than read off the source turns one DDL statement into a full-table conflict storm at the next `verify` tick (`connectors.md:154-158,204`). |
| The read-time default is a **fallback, not a derivation**: it stops applying to a row the moment that field is written on it. "Nothing is backfilled" holds per row until the first write. | `schema/evolution.md` | `traits.md:293`'s `scheduled_at` is a live case of a defaulted field later mutated (`events.md:231`). |
| Read the default from the schema node **current for the row version being read**, not "the node that added the field" — which may not be unique (a two-parent merge where both branches added it, `transaction-graph.md:77-80`; a field deprecated and re-declared). | `schema/evolution.md`, in the rule itself | A per-row-version fact the version chain already carries, versus a schema-graph fact that may be ambiguous. |
| The adding node is **pinned against `prune`** by every row older than it, and one field may carry N generations of default. | `schema/evolution.md#coercion-between-schema-nodes`, beside `:193-214` | Same shape as "a degenerate dependent blocks deprecation" (`evolution.md:204-211`). Without it, `prune` makes old rows unreadable. |
| `deprecate <table>.<field>` is rejected while a live field's default mentions that field. | `schema/evolution.md`, under Deprecate and prune | Otherwise a default resolves against data the query layer has been told does not exist. Fires only on defaults predating the row-6 restriction. |
| "Nothing is backfilled" is true of the **`table` redeclaration path only**. `Customer = Customer { *, Bronze as loyalty_tier }` adds a column as a binding, is frozen into storage (`evolution.md:21-23`), and is a full rewrite — and that is the **documented escape** for the defaults rows 8, 11, 13 and 14 reject. | `schema/evolution.md`, narrowing the claim and naming the escape | Two spellings for one edit with opposite cost and opposite rules, and nothing today tells an author which they wrote. |
| Rule A cannot reach a derived table, and the grammar enforces that rather than a check: a `Binding` (`railroad.md:197`) has no body in which to write a `FieldDecl`. | `schema/queries.md#keys-are-computed-never-declared`, one sentence | So a reader does not conclude the case was overlooked. |
| Rule A binds DataCode's own `system.*` tables and its upgrade path — a version upgrade adding a field to `system.auth.*` ships a default and cannot backfill an operator's rows. | `schema/README.md#self-hosting-principle` | "The schema is data" makes the product's own author even less able to see the data than an application author. |
| A literal default on an added `Secret`, `Hashed`, or `Encrypted` field is rejected: one digest, or one known plaintext, on every pre-existing row. The sound shape is `T \| NotGiven = NotGiven`. | `schema/types.md#secret-types`, bullet beside `railroad.md:165-167` | Same list as `unique`/`indexed`/`order by` on a `Secret` field, and the reason is stronger — a disclosure, not an unenforceable constraint. |
| Cap'n Proto's implicit zero must be explicitly ordered **under** DataCode's declared default. | `storage.md`, where the wire format's evolution properties are claimed | A row written under an older node decodes short; the encoder answers 0 where the schema says 42 (`storage.md:186-187`, `tech-stack.md:88`). Rule A is what makes a short decode's semantics well defined. |
| The rejection diagnostic must spell a **two-step, two-language** path, not "a bulk mutation". | `railroad.md`, the new `FieldDecl` bullet's diagnostic text | `Mutation` (`railroad.md:634`) lives in the query grammar, not `Statement` (`railroad.md:69-81`), so it cannot appear in a `.dc` file. |
| An added field's `where` block interacts with the mode rule deterministically: for a closed default the blast radius is 0% or 100%. If the default satisfies its predicate, no mode is required; if it fails, reject outright. | `integrity.md`, in Mode Is Mandatory on a Populated Field | The mode mechanism is for rows the author did not write. A default is a row value the author *did* write, so three modes is a decision with no content. |
| The intra-declaration default cycle (`a : Int = b, b : Int = a`) is unrejected and must be checked at schema commit. | `railroad.md` `FieldDecl` bullet; rationale in `tables.md` | Structurally identical to `functions.md:239-241`'s acyclic call graph over function columns, decidable for the same reason. The *evolution* case needs no check: a default at node N can only mention fields existing at N, so every edge points strictly backwards. |

### Rule B

| Consequence | Normative home | Why |
|---|---|---|
| The record's identifier fields are **row keys**, not `DataId`s: `head_index`'s key (`storage.md:43-45`) — a `DataId`, or a `DataId` plus one `Ordinal` per nesting level. | `storage.md` § 1, the frame | Only shape that can name a component reparent, which is the case `00-report.md:224` created. No new machinery; the rendered form is already user-visible. |
| Five fields, not two: `{ table, old row key, new row key, old shard root, new shard root }`. No reason, no authority. | `storage.md` § 1 | A bare id does not name a table (`integrity.md:217-227`; `datacode.capnp:37`'s delete carries only the id). Neither participant can derive the other's root — the source holds the tombstone with the old root, the destination the successor with the new. No reason because a re-key destroys nothing (`ReasonClause` is mandatory on `erase`/`scrub` precisely because they do, `integrity.md:420`); no authority because it is recoverable through `system.logs.HttpRequest.tx_id` (`api.md:199-200`). |
| **Equality of the two roots** is how a reader tells a same-shard re-key from a cross-shard one. No flag, no node kind, no second shape. | `storage.md` § 1 | Derives the distinction rather than declaring it, the move `transaction-graph.md:168-174` already makes for shard rooting. |
| Both prepared nodes carry an **identical** record; the commit node carries none; nothing in the record may be a value unknown at prepare time (so: not the commit node's id, not the outcome). | `distribution.md#cross-shard-transactions` | A record on A alone is invisible to B forever (`distribution.md:412,425`), defeating the property for the reader who needs it. B writes at step 3; A appends the commit node at step 4. |
| The record **inherits its carrier node's visibility** and is a historical statement about one transaction — "at this transaction, this row key was superseded by that one" — not a live `successor` pointer. `show transaction` renders a record on an unresolved or aborted prepared node as pending or aborted, never as a move. | `storage.md` § 1; cross-ref from `queries.md:584-587` | A prepared node's outcome is not a local fact on B, and a tombstone is resurrectable (`queries.md:587`). |
| The record must **never be load-bearing for applying a transaction**. An old decoder that ignores the field applies the delete and the insert correctly and loses only the link. | `storage.md#wire-format-for-replication` | This is what keeps the frame additively evolvable and what `distribution.md:30-35`'s rolling upgrade depends on. |
| Add it as a new top-level `TxNode` field, **not** as a third `Mutation` union member, even though the union is cheaper. | `storage.md#wire-format-for-replication` | Union compatibility is weaker than field compatibility: an old secondary seeing an unknown tag applies the transaction and drops the variant — silent divergence, not a decode error. It is also an *annotation over* the mutation list, not another mutation. |
| It is a **list**, and a bulk or cluster-wide re-key produces one list per shard. | `storage.md` § 1 | `distribution.md:459-489` makes a bulk mutation per-shard and possibly partial; records follow the mutations they annotate. |
| The pairing is **not derivable** from the mutation list — that, not legibility, is why the record must be explicit. Two rows of one table re-keyed in one transaction cannot be matched, because the values that would disambiguate them are exactly the ones that changed. | `storage.md` § 1 | Converts the record from a convenience into a necessity, and is the argument the decision is missing. |
| Old→new on the source shard is not enough. A server-local, unreplicated **new→old index** derived from the nodes — the same posture as `PhysicalLocator` (`transaction-graph.md:530-533`) and the same cache-not-source-of-truth argument as `FieldTimeCache` (`:663-672`) — is what closes the gap. | `storage.md`, cross-ref from `transaction-graph.md` | Every consumer starts from the successor. Without it "queryable" means "scannable". |
| **One sentence covers the version chain and events**: the predecessor's post-state is the successor's pre-state. The version-chain walk follows the link (`Table.field.updated_at` therefore does not report every field as changed at the move), and an `on` condition is a transition across the link — so `on customer == vip` correctly fires and `on status is Shipped` correctly stays silent. | `transaction-graph.md#per-field-timestamps` and `events.md#on` | Without it, `events.md:99-104` makes every true condition re-fire on the insert half: a second shipment email for a shipment that already happened. |
| The walk **terminates at an `erase` on a predecessor**, and the field then reads its value as of the re-key and no earlier. An uncached walk crosses a shard, so `FieldTimeRequest.versions_walked` (`transaction-graph.md:695-699`) must count the hop or the cache proposal undercounts. | `integrity.md#erasure-is-restriction-of-processing`; `transaction-graph.md#declaring-and-proposing-the-cache` | `integrity.md:370-372` closes history at every earlier moment; a walk through it would reconstruct what erasure closed. |
| **A bare `DataId` resolves through the re-key chain.** One rule fixes `TriggerState.subject` (`events.md:183-188`), `Violation.subject` (`integrity.md:215-227`), and a queue payload's captured `id` (`events.md:83-88`). | `transaction-graph.md`, with the record | `TriggerState` is `LogData` and append-only, so rewriting rows means an insert per `every` trigger per re-key. The successor otherwise has no held bit and the `every` scheduler re-fires. |
| Component ordinals are **preserved** across a re-key, not reassigned — which is what makes one key pair sufficient for the whole subtree, by prefix substitution. Allocation on the successor seeds from the copied `max + 1`, importing the predecessor's gaps. | `transaction-graph.md#component-ordinals` | Reassignment renumbers every array in every `Doc indexed` field, because an array element's identity *is* its ordinal (`documents.md:103-105`), and needs O(subtree) bytes of mapping on the node. Preservation keeps "never reused" (`:487`) true. Fix `documents.md:103`'s "contiguous" in the same pass — already false after any component delete. |
| A re-key **resets `created_at` and `origin_server`** on the row and its whole component subtree, which restarts any `retain` window (`aggregates.md:218`) and any `Behavior` closing over `created_at` (`types.md:298`). `created_at` has the declared-`Timestamp` escape (`transaction-graph.md:642-643`, `aggregates.md:219-230`'s `using`); `origin_server` has none — a table needing provenance across a re-key declares a `:> system.shards.Node` field. | `transaction-graph.md#virtual-columns` and `schema/aggregates.md#time-source` | Value changes with no write to any stored field — the class of thing "time is a parameter, never ambient" exists to prevent, arriving through the identifier instead of the clock. |
| The **`erase` cascade must follow re-key links forward, transitively**, from every row in the erased subtree. | `integrity.md#erasure-is-restriction-of-processing` | Delete-plus-insert copies every non-key field into the destination shard. `erase C1` walks FK chains (`integrity.md:386-388`) and reaches the tombstone, not the byte-for-byte copy under C2. The copy was created by the system, so nobody remembers it exists. |
| Conversely, the record **survives** erasure of the predecessor's root and discloses that a row left that subtree; counterpart identifiers must render `Erased` for a token without `bypass erasure`. | `integrity.md#erasure-is-restriction-of-processing` | Transaction nodes are immutable (`:19,378-380`), so the residue is real; same honest-disclosure posture as a scrub node recording what it destroyed (`:414-418`), and the same treatment `observed` already gets (`:278-279`). |
| The tombstone of a re-keyed row is **terminal**: a write at the old key is rejected, naming the successor. | `schema/queries.md#delete-appends-a-version` | `queries.md:587` plus `distribution.md:326` otherwise permit resurrecting the predecessor at a still-reserved key while the successor is live — two live rows for one entity, one recorded as superseded. |
| No sample moment sees both rows, so **no aggregate double-counts**; and `diff` reports `Removed` + `Added`, never `Changed`, provably — every non-degenerate derived key over the table contains the placement key, whose value changed (`queries.md:454,469-470,382-385`). `diff` should not learn about the link; `show transaction` is where it is read. | `schema/queries.md`, sample moment and diff sections | One commit node, one moment resolved by the coordinator (`queries.md:401-402`). ## (E) Anything still open

1. **Does a re-key trigger on any placement-key field change, or only on a change of shard root?** The literal rule makes changing `Order.order_num` — a non-head field of `unique orderRef { customer, order_num }` — a delete-plus-insert with a new `DataId`, a severed chain, re-fired events and dangling subjects, while the stated harm (an invalidated shard-bounded `Ordinal`, a key that stops reaching its root, `00-report.md:208-213`) does not occur. **Recommend the narrow rule: delete-plus-insert applies exactly when the write changes the row's shard root.** The root is computable from the FK chain at write time, so it is decidable, and it is the rule the justification actually supports.
2. **How is the gate restated, and what happens to root tables?** As written it admits a colliding second `unique` and rejects every root candidate-key change. **Recommend two changes: state the gate as "every `unique` on the table is headed by the placement key's own head field"** (unambiguous, strictly stronger, and what `00-report.md:263-265`'s own example demonstrates); **and state that a root row's candidate-key change is not a re-key** — a shard is named by its root row's `DataId` (`transaction-graph.md:158-159,446`), which does not move, so nothing crosses shards and no ordinal is invalidated. It is an ordinary update plus a shard-directory write plus a possible range-tree re-resolution.
3. **Is a component reparent permitted, and how is it named?** Two coherent answers. **Recommend: type the record over `head_index` keys and permit reparenting only within the same shard root**, keeping `traits.md:220` re-derived as a prohibition on shard-crossing (which `transaction-graph.md:490` already implies). The key type is needed regardless, to name the subtree that moves with an ordinary parent.
4. **Does the `erase` cascade follow re-key links, or is re-key forbidden on tables carrying `Personal`?** Following is the honest answer and needs the new→old index; forbidding is cheaper and takes a routine operation away. **Recommend following, transitively forward, with an outbound-edge entry in the erase report** shaped like the cross-shard FK warning at `constraints.md:187-189` — the FK chain simply stopped being a complete account of reachability.
5. **Is the transaction graph self-hosted as `system.graph.Transaction`?** "Queryable" depends on it, `show transactions` needs an access story, and the review's structural defect 6 wants it for routing. **Recommend declaring it** — the self-hosting principle (`integrity.md:299-302`) is what makes violations queryable, and Rule B currently claims a property only the alternative it rejected has.
6. **What does an existing rollup bucket read for a column added to a live chain, and where is it spelled?** `ProjItem` (`railroad.md:627-630`) has no slot for a default or a type. **Recommend reusing `aggregates.md:275-282`: an aggregate column added to a chain that has levels is typed `T | NotRetained` and the chain rejects it otherwise** — by a generation rule that widens the level table's column, not by new `ProjItem` syntax. Note that this is a *type* requirement, not a default requirement, and Rule A as phrased would forbid it.
7. **Is re-declaring a deprecated field an add?** Both answers break something: "yes" makes rows written before the deprecation read the default instead of their stored value; "no" leaves rows written while the field was hidden undefined. Nothing forces the re-declared type to match, either. **Recommend a field-identity rule mirroring the tag rule at `evolution.md:229-231`:** a field path, once declared, is bound to its declared type for the life of the table; re-declaring it with the identical type is an un-deprecate needing no default; a different type is rejected with "choose a new name."
8. **Where does a `Violation` on a re-keyed row live** — rewritten into the destination shard by the re-key transaction, or left in the source shard and resolved forward? `enforce forward`'s grandfathering behaves differently under each. **Recommend resolving forward** (the violation is a historical fact about a transaction, and rewriting it would put a system write inside a user mutation), which makes the resolution rule from (C) load-bearing rather than convenient.
9. **Does the re-key link participate in merge reconciliation as a key alias, or is a re-key rejected on an unmerged branch?** Merge semantics are undesigned (`00-report.md:957` defers the supplied-field mask for the same reason), and a re-key on a branch yields a duplicate of one entity that reconciliation by candidate key cannot see. **Recommend deferring with the dependency recorded** rather than deciding it inside this rule — but record it, because it is invisible from either rule alone.
10. **Which rejection is normative for `owner :> User = { name = "x" }`** — an unspecified construction, or a cross-table in-commit write (`events.md:480-484`)? The grammar admits it (`railroad.md:488`) and nothing rejects it today. Minor, but it is a design call rather than an oversight.

Anything else you want folded in — a different reading of the gate, or a preference on 5 and 6, which are the two that change other files most?
