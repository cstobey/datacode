# Table definitions

See [README.md](README.md) for the `:` / `:>` rule, clause order, `where`, and the
termination and layout rules assumed here.

## Basic syntax

```
-- DataId primary key is always implicit — no declaration needed
-- Namespace created implicitly on first use
table app.commerce.Customer {
  email        : Email,
  name         : Text,
  status       : Active | Suspended | Closed,
  phone        : Phone | NotGiven,
  loyalty_tier : Tier = Bronze      -- field default with =
}
```

Field declarations are separated by `,`; the body is closed by `}`. A comma before the
closing `}` is permitted. Where any field carries a block `where`, put the separator at the
start of the next declaration instead — see below.

Every table has four automatic virtual columns:

- `id` — the row's own `DataId`, rendered as 20 characters of Crockford base32
- `created_at` — timestamp extracted from the row's `DataId`
- `origin_server` — the issuing server, extracted from the row's `DataId`, typed `:> system.shards.Node`
- `updated_at` — timestamp of the most recent `PhysicalLocator` that mutated the row

The first three are projections of the row's identifier and cost no bytes and no lookup. The
sequence counter is also in the `DataId` and is deliberately *not* exposed — it is a tiebreak
within one server-millisecond, not an ordering. `PhysicalLocator` (the physical address of one
row version) is internal only and likewise not exposed in the schema DSL. See
[../transaction-graph.md](../transaction-graph.md#virtual-columns).

`id` is how an update or a delete names one row —
`Order where id == "05KG3N0000ZQ8V4T1H7C"` — and how an event payload captures the row it
fired on. It is a `DataId`, never a uuid. It is excluded from candidate keys for the reason
under [Candidate keys](#candidate-keys-are-mandatory): the surrogate always exists, so
counting it would make the rule vacuous. A `Component` row has no `id`, because it has no
`DataId`; it is named by its parent's `id` plus one `ordinal` per nesting level, which is the
same row key the storage index uses ([../storage.md](../storage.md)).

`created_at` and `updated_at` are also available **per field** — `Order.status.updated_at` is
when `status` last changed, as distinct from when the row last changed. Per-field timestamps
are computed from the row's version chain and never stored on the row; which fields keep a
cache of them is a `Configuration` row, and the maintenance queue proposes additions from
observed usage. See
[../transaction-graph.md](../transaction-graph.md#per-field-timestamps).

A table carrying the `Component` trait has no `DataId` of its own; its rows are identified by
the parent's identifier plus an `Ordinal`, and both `created_at` and `origin_server` are
inherited from the parent. It trades `id` for `ordinal`, its position under that parent, which
is how document order is stated in a query. See [traits.md](traits.md#component).

The inheritance is worth deciding at declaration time rather than discovering later:
**a component's `created_at` is its parent's.** A component that needs its own creation time
declares a `Timestamp` field and writes it. There is no equivalent escape for
`origin_server` — a component that needs provenance of its own declares a
`:> system.shards.Node` field.

A table generated by a retention chain also has `grain`, the width of its time bucket. Like the
others it costs no bytes — it is constant for the whole table — and like them it is queryable,
so `RequestRollup where grain == Hour` selects one level. See
[aggregates.md](aggregates.md#grain-is-a-virtual-column).

Redeclaring a table diffs it against the previous version. Write `*` in the body to carry
forward every field the new body does not mention. See
[evolution.md](evolution.md#redeclare-a-table).

## Field declarations

A field declaration is a name, a type token, a type, and up to seven trailing clauses in a
fixed order ([README.md](README.md#clause-order) owns the order):

```
field ( ":" | ":>" ) Type
      [ : Traits ]                      -- sub-table traits
      [ { street : Text, … } ]          -- sub-table body
      [ [ { name = "a" }, … ] ]         -- seed rows, Reference sub-tables only
      [ unique ] [ indexed ] [ = Default ] [ where Predicate ]
```

The first three are the sub-table clauses and are valid only with `:>`. Their position — before
`unique`, and before the default — is what makes
`settings :> Settings : Component = { theme = Dark }` read the way it does.

```
table app.commerce.Order {
  loyalty_tier : Tier   = Bronze,
  name         : Text   = "Unknown",
  is_active    : Bool   = True,
  email        : Email  unique where isCorporateDomain,
  total        : Amount = 0 where \a -> a >= 0
}
```

The default precedes `where` so that an `=` inside the predicate is never mistaken for a
field default.

A default is optional on a table being declared for the first time and **mandatory on a field
added to a table that already exists**, where it must be `Pure` and stable for the life of the
row — every older row computes it at read, and nothing is backfilled. The rule, the criterion,
and the form-by-form table belong to evolution; see
[evolution.md](evolution.md#redeclare-a-table).

A default may name another field of the same declaration, so the defaults in one body must
form an acyclic graph: `a : Int = b, b : Int = a` denotes nothing and is rejected at schema
commit. That is the same check the call graph over column-valued functions already needs, and
it is decidable for the same reason. The evolution case needs no check — a default written at
one schema node can only mention fields that exist at that node, so every edge points strictly
backwards.

`indexed` sits beside `unique` because both are storage hints rather than parts of the
field's meaning. It is currently valid only on a `Doc` field, where it requests the shredded
form — see [documents.md](documents.md#storage-bytes-first-shredded-second).

### Validation blocks

One `where` per field. Several predicates go in an indented block beneath it, implicitly
conjoined. Use leading commas so the separator does not strand itself after the block:

```
table app.commerce.Customer {
  email : Email unique
    where
      isValidEmail
      maxLen 254
      \e -> not (isDisposableDomain e)
  , name : Text
    where isNotEmpty
  , phone : Phone | NotGiven
}
```

A field's validation is addressed by the field's path —
`app.commerce.Customer.email` denotes both the computed field type and the predicates on it.
There is no separate name for it. See
[README.md](README.md#addressing-validations).

## Uniqueness constraints

```
-- Single-field: `unique` keyword suffix
email : Email unique

-- Multi-field: named constraint in table body
table Order {
  customer  :> Customer,
  order_num : Int,
  unique orderRef { customer, order_num }
}

-- Standalone post-definition (add after table exists)
unique Order.orderRef { customer, order_num }
```

Multiple unique constraints per table are all enforced. `DataId` remains the primary key;
unique constraints define natural keys used for fast lookup.

## Candidate keys are mandatory

> **A table must declare a candidate key unless it carries `LogData`, `Component`, or
> `Keyless`. Omitting one is a compile-time error.**

`DataId` does not satisfy this. The surrogate key always exists, so counting it would make
the rule vacuous — the point is to say what identifies a row *other* than the identifier the
system minted for it.

The rule earns its keep in three places that already exist:

- **Merge reconciliation.** When two branches diverge and are merged, `DataId` cannot tell
  the system that both inserted "the same" customer — they minted different ids. Only a
  natural key can. See [../transaction-graph.md](../transaction-graph.md). Reconciliation by
  natural key does not see a re-key: the branch presents a tombstone at the old key and an
  apparently unrelated row at the new one (see [Changing a placement
  key](#changing-a-placement-key)).
- **Default ordering.** "System default: candidate key ascending", below, has no meaning on a
  table with no candidate key. The rule closes that for every keyed table, and the identifier
  closes the exempt ones — see [Default ordering](#default-ordering).
- **Idempotent ingest.** Replaying a connector stream needs upsert-by-natural-key.

### What is exempt, and why

The exemption is not "logs are special". It is:

> **Occurrences have no identity beyond their occurrence. Entities do.**

Two identical enqueues are two distinct work items and collapsing them would be a bug; two
identical log lines are two events. `LogData` marks that class, and queue tables carry it for
exactly this reason. `Component` is exempt because it is already keyed — by parent plus
`Ordinal` — and `Keyless` is an explicit waiver (see
[traits.md](traits.md#keyless)).

**Exempt from needing a key is not forbidden from declaring one.** A `Component` may declare
`unique`, and it is checked within the parent, so it costs one shard-local check.
`unique linkRef { order_ref, tag }` on a component of `Order` means "this order has at most one
link to this tag", which is the whole of what a many:many link table needs. See [Component
sub-tables](#component-sub-tables).

### Keys must be rooted

On a shard-local table the key also determines placement, so it is constrained:

> **A candidate key on a `UserData` table must be rooted: either it contains no same-family
> foreign key, in which case the table *is* a shard root, or its foreign-key chain reaches
> one.**

The chain may be transitive. `unique orderRef { customer, order_num }` names the root
directly; `unique lineRef { order_ref, product }` on an order line does not, but `order_ref` is
an FK to a table that is itself rooted at `Customer`, so placement is still determined. Foreign
keys to `Reference` and `Configuration` tables do not participate — those are replicated
everywhere and say nothing about placement.

The field is `order_ref` rather than `order` because `order` is reserved by `order by`. See
[railroad.md](railroad.md#words-a-schema-wants-and-does-not-get).

Three consequences worth stating plainly:

- **A `UserData` table whose key contains no same-family FK *is* a shard root.** No separate
  keyword is needed to declare shard rooting; the key declaration already says it, and it
  cannot drift, because adding an FK to a table changes nothing unless you put it in the key.
- **Where a key reaches two distinct roots**, the first *participating* FK in the key
  declaration determines placement. This is the same head rule that governs `:>` alternations.
  Key field order is therefore significant for placement even though a key is otherwise a set
  of attributes: reordering the fields of a declared key repartitions the table.
- **A link table with two `:>` fields lands in one side's shard family**, decided by that same
  head rule. The asymmetry is unavoidable — a row lives in one shard — so choose it
  deliberately rather than by declaration order. See [Component
  sub-tables](#component-sub-tables) for when the link should be a component of the owning
  side instead.

This rule is about `UserData`, where the root's candidate key happens to serve two jobs at
once. They are separable: identity asks *which row is this*, placement asks only for a **total
order**, and `DataId` supplies one on every table including the keyless ones. A `LogData`
table therefore has placement without having a key — it is rooted at a
`system.shards.LogSegment` row instead, and its own rows stay keyless. See
[../transaction-graph.md](../transaction-graph.md#placement-keys-are-not-identity-keys).

The root table's own key is the one that is **not** shard-local — every user lives in a
different shard, so `username unique` on the root is a cluster-wide constraint. That index is
the shard directory (`username → DataId → shard`), which is the lookup that routes a request
to the right server, so the global constraint costs nothing extra. Every non-root key is
checked within one shard and needs no coordination. See
[../transaction-graph.md](../transaction-graph.md#shard-roots).

### Changing a placement key

A rooted key names the shard the row lives in, so changing it moves the row. That has one
rule, and it needs no new machinery:

> **A write that changes a row's shard root is not an update. It is a delete and an insert.**

The chain that gets there is short. A foreign-key functor resolves to a **live** row
([functors.md](functors.md)), so an FK can name a deleted row only where the field carries a
`Null`-derived tail — and a placement-key FK never can, because a `Null`-derived variant is
rejected in a key ([Ineligible key fields](#ineligible-key-fields)). So a rooted key, and a
shard-bounded `Ordinal` under it, can be invalidated by exactly one thing: the placement-key FK
being updated. A delete in shard A plus an insert in shard B is then an ordinary
two-participant transaction, already specified in
[../distribution.md](../distribution.md#cross-shard-transactions).

The rule is general rather than `Component`-specific, because two rules for one situation would
be worse than one. It replaces three things that would otherwise have to exist: a recorded
cross-shard migration, a standalone "a component cannot be reparented" invariant
([traits.md](traits.md#component)), and any rule about placement-key mutability.

**The trigger is a change of shard root, not of any placement-key field.** Changing
`Order.order_num` — a non-head field of `unique orderRef { customer, order_num }` — is an
ordinary update: the shard root is unchanged, so no `Ordinal` is invalidated and nothing
crosses a shard. Changing `Order.customer` is a re-key.

**A root table's candidate-key change is not a re-key either.** A shard is named by its root
row's `DataId` ([../transaction-graph.md](../transaction-graph.md#shard-roots)), which does not
move, so a username change or a branch rename crosses no shard and invalidates no ordinal. It
is an ordinary update plus a shard-directory write.

#### The gate

> **Delete-plus-insert applies only where every `unique` on the table is headed by the
> placement key's own head field.** Where any other `unique` is table-wide, or headed
> elsewhere, the write is rejected with a diagnostic naming the constraint.

The gate is not decoration. Two things go wrong without it:

- **A second `unique` collides with its own tombstone.** The placement key itself is safe,
  because the trigger for the operation is that its value changed. Any *other* `unique` on the
  row keeps its value: the delete tombstones the row, a tombstone does not free the reserved
  value ([../distribution.md](../distribution.md#a-reserved-value-is-released-only-deliberately)),
  and the insert then writes the same value and is rejected. A table-wide `unique` served by a
  constraint shard fails this way every time.
- **A `unique` headed elsewhere silently changes what it means.** A non-root key is checked
  within one shard, and that shard is the row's — decided by the placement key's head. A
  `unique` headed at a *different* root is therefore checked against whichever population the
  row currently sits among, and moving the row changes that population with none of the
  constraint's own values changing. That is a semantic change with no write behind it.

The head is what matters, not every field. `unique linkRef { order_ref, tag }` on a component of
`Order` is headed by `order_ref`, so it qualifies.

Where the gate fails, the escape is the existing one and it is deliberately manual: `release`
the offending value, with its mandatory authority and reason, then re-key. Auto-releasing
inside an ordinary update would defeat the property that a reserved value is released only
deliberately, and it would put an erasure command inside the query language.

#### What a re-key costs

- **A row with live inbound references cannot be deleted, so it cannot be re-keyed.** Moving a
  row across shards while other rows point at it is the hard case, and rejecting it is better
  than a silent distributed rewrite. See [Deleting a referenced row](#deleting-a-referenced-row).
- **The row's `DataId` changes.** It genuinely became a different row in a different shard.
  The predecessor's history stays readable under its own id, and the two are linked by a record
  on the transaction node rather than by a column on either row — a supersession is a fact about
  a transaction. See [../storage.md](../storage.md).
- **The component subtree moves with the parent**, ordinals preserved rather than reassigned,
  which is what lets one key pair name the whole subtree by prefix substitution. Reparenting a
  component within the same shard root is permitted; across roots it is not. See
  [../transaction-graph.md](../transaction-graph.md#component-ordinals).
- **`created_at` and `origin_server` reset**, because both are projections of the new
  identifier. That restarts any `retain` window and any `Behavior` closing over `created_at`.
  `created_at` has the declared-`Timestamp` escape; `origin_server` has none.

### The error

```
datacode[app.commerce]> :commit
error: app.commerce.Order carries UserData and declares no candidate key.
       Declare one:
         order_num : Int unique                   -- single-field, first declaration only
         unique orderRef { customer, order_num }  -- multi-field, over existing fields
       Or waive it, which is recorded in system.integrity:
         table app.commerce.Order : UserData, Keyless { … }
```

The first remedy is offered only where the table is being declared for the first time. **No
`unique` field may be added to a table that already has rows**: every admissible default for an
added field is constant, so it collides with itself on the second row, and no injective
row-local expression is spellable ([evolution.md](evolution.md#redeclare-a-table)). The path
there is a rebuild — bind a derived table over the superseded one that computes the key column,
which freezes into storage and is a full rewrite rather than a read-time default. The
multi-field remedy is unaffected, because it constrains fields that already exist.

### Ineligible key fields

This table is the single home for the list. It governs both spellings — a `FieldPath` named by
a `unique <name> { … }` constraint, and the inline `unique` marker on a field declaration.

| Rejected in a key | Reason |
|---|---|
| A type including a `Null`-derived variant | `MissingCustomer` is an ordinary value, so two rows carrying it genuinely collide — the constraint would permit exactly one keyless row. Coherent, but never what anyone means. |
| A `Secret` or `Hashed` field | Already a compile-time error; per-row salts make it unenforceable |
| A `Doc` field | Unbounded and shape-unknown |
| A `Behavior` field | Its value changes with no write |
| A function-typed field | Function types have no equality — see [functions.md](functions.md#restrictions) |
| A table-valued `:>` field | It denotes a set of rows, not a value — see [Component sub-tables](#component-sub-tables) |
| `id` | The surrogate always exists, so counting it would make the key rule vacuous |
| `updated_at` | It changes on *every* write, so the row would not keep its identity across an update |

**The other virtual columns are eligible**, and `system.shards.LogSegment` keys on one —
`unique segmentRef { origin_server, period_start, branch }`, where `origin_server` is declared
nowhere ([../transaction-graph.md](../transaction-graph.md#logdata-shard-roots)). `created_at`,
`origin_server`, `ordinal`, and `grain` are all immutable for the life of the row's `DataId`,
which is the only property a key field needs; that they are projections rather than stored bytes
is irrelevant to uniqueness and saves the schema a declared copy free to disagree with its
source. `updated_at` is excluded for the same reason `Behavior` is — not because it is virtual,
but because it moves.

The qualification matters in one case only: a re-key mints a new `DataId`, so `created_at` and
`origin_server` take new values on the successor row (see [Changing a placement
key](#changing-a-placement-key)). Within one `DataId` they never move.

The `Null` case is worth noting as somewhere the absence of `NULL` pays off: SQL has to pick
a vendor-specific rule for nulls in a unique index, and DataCode does not have the ambiguity at
all — which is what lets the rule be strict.

> Short examples throughout these documents elide the key declaration when they are
> illustrating something else. A three-line fragment showing `order by` or an `assert` is not
> a complete table and would not compile as written.

## Sequences

`next <UniqueName>` in a default allocates the next value in a sequence:

```
table app.commerce.Order : UserData {
  customer  :> Customer,
  order_num : Int = next orderRef,
  unique orderRef { customer, order_num }
}

table app.billing.Invoice : UserData {
  invoice_num : Int = next invoiceNum,
  unique invoiceNum { invoice_num }
}
```

> **The scope of a sequence is the scope of the uniqueness it serves.**

`next` allocates within the named `unique` constraint's field list **minus the field being
defaulted**. That one rule produces both cases without the author declaring a scope twice:

| Declaration | Sequence scope | Coordination |
|---|---|---|
| `unique orderRef { customer, order_num }` | per `customer` | none — local to that shard |
| `unique invoiceNum { invoice_num }` | table-wide | that constraint's own shard |

`orderRef`'s prefix is `customer`, so the counter lives with the customer row, and the
increment is a read-modify-write inside a transaction that already touches that shard.
`invoiceNum`'s prefix is empty, so it is table-wide and reaches the shard holding that
constraint's value index — rooted at the constraint's own schema-node row, not on the schema
shard, and splittable by value range (see
[../distribution.md](../distribution.md#constraint-shards)). Exactly like a table-wide `unique`
constraint, and for the same reason. **The shard cost is readable off the declaration**, because
it is the same prefix-reaches-the-root question the candidate key already asks (see [Candidate
keys](#candidate-keys-are-mandatory)).

Four consequences:

- **A table-wide `next` warns at schema commit**, naming the serialization it introduces —
  every insert to that table will queue behind the constraint's shard. A prefixed `next` whose
  prefix reaches the shard root warns about nothing, because it costs nothing. The same
  diagnostic prices a `Component` whose ordinal allocation serializes on its parent (see
  [Component sub-tables](#component-sub-tables)).
- **`next` may only be declared when the table is created.** A field defaulted with `next` and
  added to an existing table is rejected: `next` allocates rather than evaluates, so it is the
  one genuinely transactional default, and a row committed last year has no transaction in
  which to allocate. See [evolution.md](evolution.md#redeclare-a-table).
- **Gaps are guaranteed.** An aborted transaction burns a value. Nobody gets gapless sequences
  without serializing every insert, and where the number is externally meaningful — invoice
  numbers an auditor will read — gapless is a *reporting* requirement satisfied by a query over
  the log, not by the allocator.
- **`next` is an allocation, not a value.** It is admissible only in a `DefaultClause`, only on
  a field the named `unique` includes, and is rejected in a `where`, a `Behavior` definition, a
  projection, and a binding.

Counter storage is one row per (constraint, prefix value), sharded by the prefix — the same
sharding rule as everything else. Layout numbers are open with the other sharding numbers in
[OQ-035](../open-questions.md#oq-035-extent-size-segment-period-and-shard-group-formation).

## Behavior fields

A field whose type is `Behavior a` is computed from the row at the moment it is observed
rather than stored. Full treatment in [types.md](types.md#behaviors):

```
table app.billing.Loan : UserData {
  customer  :> Customer,
  principal : Amount,
  rate      : Rate,
  opened_at : Timestamp,

  unique loanRef { customer, opened_at },

  balance : Behavior Amount = \t -> principal * (1 + rate * (t - opened_at) / day)
}
```

The `=` clause is the definition, not a default, and is mandatory. `unique`, `indexed`,
`order by`, and `where` are all rejected on a behavior field, and a behavior may not appear
in a row construction or update literal. See [types.md](types.md#restrictions).

## Default ordering

```
table Order {
  customer  :> Customer,
  order_num : Int,
  placed_at : Timestamp,
  total     : Amount,
  unique orderRef { customer, order_num },
  order by placed_at desc    -- default ordering for queries against this table
}
```

System default, where no `order by` is declared: candidate key ascending. Overridable
per-query. This is well defined for a keyed table precisely because a candidate key is
mandatory — see above.

On the three exempt classes there is no candidate key, so the identifier supplies the order
instead: **`id` ascending on a `LogData` or `Keyless` table, `ordinal` ascending within the
parent on a `Component`.** A `DataId` is monotone and total, so this is a real ordering rather
than a fallback, and it is what keeps every queue and every log deterministically ordered.

**A declared order is extended by the candidate key as a final tiebreak.** `order by placed_at
desc` is not total on its own — fifty orders sharing a timestamp would put a page boundary
mid-tie — so the effective ordering is `placed_at desc` followed by the key. See
[queries.md](queries.md#ordering).

## Foreign keys

`:>` declares a field that references a row in another table. It creates a field-scoped
type (`namespace.table.field`) wrapping the referenced table's `DataId`, attaches an FK
functor (kind 2 — see [functors.md](functors.md)), and adds an edge to the join graph used
by `><`.

```
table app.commerce.Order {
  customer  :> Customer,      -- FK to Customer; creates Order.customer type
  placed_at : Timestamp,
  total     : Amount
}
```

`:>` is required whenever the head of the type expression names a table or derived table. Writing
`customer : Customer` is a compile-time error, as is `email :> Email` where `Email` is a
type.

**One `:>` field is single-valued and one is table-valued, and the target's trait is what
decides which.** A `:>` to an ordinary table wraps one `DataId`. A `:>` whose target carries
`Component` denotes every one of that parent's rows in the target, in `ordinal` order — see
[Component sub-tables](#component-sub-tables).

### Deleting a referenced row

> **Deleting a row that live, non-`Component` references point at is rejected.**

This is `RESTRICT`, and it follows from the foreign-key functor's own signature rather than
being a new policy: the functor resolves to a **live** row
([functors.md](functors.md)), so a field with no `Null`-derived variant in its type has no
value to read once the target is gone. A field whose type carries such a variant is not a live
reference in this sense and does not block the delete.

Two scopes on it:

- It counts references from **current-state** tables only. A `LogData` row recording that
  something happened cannot acquire a veto over current state, and a log with no `retain` chain
  is never pruned, so counting it would make the delete permanently impossible.
- Deleting a parent still deletes its components, because a component is not an independent
  reference — see [Component sub-tables](#component-sub-tables).

### Nullable and fallback references

The head rule allows absence types and further tables in the tail:

```
-- Reference may be absent; the reason is typed
table app.commerce.Order {
  customer :> Customer | MissingCustomer
}

-- Fallback chain: resolve against Customer, else HistoricalCustomer, else absent
table app.commerce.Order {
  customer :> Customer | HistoricalCustomer | MissingCustomer
}
```

The field's type is the full sum. The FK functor applies only to the table variants;
`Null`-derived variants carry no reference and always match. This mirrors outer-join guard
semantics exactly — see [queries.md](queries.md).

### Multiple references to one table

Two `:>` fields may target the same table. Queries must then name the path explicitly with
`via` (see [queries.md](queries.md)):

```
table app.commerce.Shipment {
  origin      :> Warehouse,
  destination :> Warehouse
}
```

## Inline sub-tables

Defining a table inline inside a field declaration creates the sub-table as a sibling in
the parent's namespace, and makes the field a reference to it. The token is therefore `:>`:

```
-- Creates app.commerce.Address as a sibling table;
-- Customer.address references a row in it
table app.commerce.Customer {
  address :> Address {
    street : Text,
    city   : Text,
    zip    : Zip
  }
}
```

There is no embedded product-in-row. An inline sub-table is sugar for "declare a sibling
table, then reference it", and `:>` states that plainly. The two forms below are equivalent:

```
table app.commerce.Customer {
  address :> Address { street : Text, city : Text, zip : Zip }
}
```

```
table app.commerce.Address {
  street : Text,
  city   : Text,
  zip    : Zip
}

table app.commerce.Customer {
  address :> Address
}
```

To place the sub-table in a different namespace, use a fully-qualified name in the inline
definition.

### Seeding a `Reference` sub-table

A `Reference` sub-table may carry its rows in the declaration, as a table literal after the
body, and the field may then default to one of them by query:

```
table app.commerce.Order : UserData {
  customer  :> Customer,
  order_num : Int,
  status    :> OrderStatus : Reference { name : Text unique }
                [ { name = "Pending" }, { name = "Shipped" }, { name = "Cancelled" } ]
                = OrderStatus where name == "Pending",
  unique orderRef { customer, order_num }
}
```

Every part of that is a schema act, which is why all of it belongs in one schema commit: an
inline sub-table is already sugar for "declare a sibling, then reference it", inserting a
`Reference` row is already a schema transaction ([traits.md](traits.md#reference-tables-are-code)),
and the default names a `Reference` row, which the stratification in
[railroad.md](railroad.md#fields) permits. It replaces a declaration plus N scattered insert
statements for the small code tables — `OrderStatus`, `Tier`, `Priority` — that want exactly
this.

Three constraints the grammar cannot express:

- **Seed rows are admissible only where the sub-table declares `Reference`.** On a `Component`
  or `Configuration` sub-table they would be *data* written by a schema commit, which is the
  cross-table in-commit write [../events.md](../events.md#internal-effects-are-derived-not-triggered)
  refuses.
- **The default query must resolve to exactly one row**, and the `unique` in the body is what
  guarantees it. Without that `unique` the construct is ill-formed, not merely untidy.
- **The query resolves at schema commit** and the resulting variant tag is frozen into the
  schema node. It is not re-evaluated on read.

Constructing a row as a default stays rejected everywhere else: a construction needs a
transaction, and a row committed last year has none. The one exception is a `Component` target,
whose construction is the parent's own transaction — see [A component default constructs the
row](#a-component-default-constructs-the-row).

### Component sub-tables

A sub-table that has no independent existence — it is created with its parent, lives in the
parent's shard, and is destroyed with it — declares the `Component` trait. Its rows are then
identified relative to the parent by an `Ordinal` rather than getting a `DataId` of their
own, and the reference back to the parent costs no bytes at all:

```
table app.log.Request : LogData {
  received_at : Timestamp,
  body        : Doc indexed,
  headers     :> RequestHeader : Component {
    name  : Text,
    value : Text
  }
}
```

#### A component reference is table-valued

> **`headers` holds *all* of that request's header rows, in `ordinal` order.**

That is the asymmetry to keep in mind, because it is the one place `:>` does not mean one row:

| Target | The field denotes | Cardinality |
|---|---|---|
| Any ordinary table | one row, wrapping one `DataId` | 0..1 |
| A table carrying `Component` | every row of the target under this parent | 0..2³² |

The reason is structural rather than chosen. A component has no `DataId`
([traits.md](traits.md#component)), so the field cannot be wrapping one; what it denotes is a
range scan over the parent's identifier prefix, and a range scan returns rows. **Inline 1:many
declaration therefore already exists** for owned children, which is why `:<` is scoped to
children that are *not* owned.

A table-valued field is rejected in a candidate key, in `unique`, in `order by`, and as an
operand of `==`, and is excluded from `*` unconditionally.

`ordinal` belongs to **stored** components. A nested table produced by `group`, or by a
sub-projection, has no ordinal — nothing was inserted in any order there. See
[queries.md](queries.md#grouping).

#### Cardinality is 1:many, always

**A component has exactly one parent, structurally.** The parent's `DataId` *is* the
component's identity prefix, so a second parent has nowhere to live: cardinality is 0..2³² from
the parent and exactly 1 from the child. A many:many *identity* is unrepresentable rather than
merely disallowed. The ordinal follows from the same fact rather than being a separate choice —
single parent, so the parent's id is the prefix, so an ordinal disambiguates siblings, so the
parent link costs zero bytes and the subtree is one range scan.

**A many:many *relationship* may still be implemented with a component link table**, because a
component may reference outward freely — an outbound FK creates no inbound dependency. The
discriminator is the other invariant, that nothing outside the parent's subtree may reference a
component:

> Use a `Component` for a link exactly when nothing needs to reference the **link row itself**
> from outside, and the link's lifetime is the owner's.

A `Membership` row that a `Payment` points at cannot be a component. A `Membership` row nobody
points at can be.

| Relationship | Construct | Placement |
|---|---|---|
| 1:many, wholly owned | `:>` to an inline `Component` sub-table | parent's shard; ordinals; zero-byte link |
| many:many, one side owns the link, nothing points at link rows | `Component` of that side plus an outbound `:>` to the other | the owner's shard |
| many:many, neither side owns, or link rows are referenced | a table with two `:>` fields, declared top level or through `:<` | the first participating FK in its key decides the root |
| 1:many, child outlives parent or has its own identity | a table with a `:>` back, top level or through `:<` | the child's key decides |

An outbound FK from a component may cross a shard. That is permitted, warns at commit naming
the edge, and restricts the attachment to `enforce forward`, `monitor`, or `repair` — see
[../distribution.md](../distribution.md#constraints-that-cross-shards-cannot-promise-enforce-always).

#### `Component` declares one bit: owned lifetime

`Component` is a **marker** trait, not a replication trait. It sits beside `Personal` and
`Keyless`, and `table app.commerce.OrderTag : UserData, Component` is legal. "Wherever the
parent is" is not a replication *policy* — it is what rooted placement already means — and the
row's real replication answer comes from `UserData`. This replaces the earlier rule that
`Component` occupied the same slot as `UserData` or `LogData`.

So many:many becomes ordinary:

```
table app.commerce.OrderTag : UserData, Component {
  order_ref :> Order,
  tag       :> Tag,
  unique linkRef { order_ref, tag }
}
```

The ordinal is the surrogate and `linkRef` is the natural key — exactly parallel to `DataId`
plus a candidate key on any other table.

Everything else `Component` used to bundle is derived rather than declared:

- **The ordinal representation is derived.** Eligibility is mechanical: the key's head is an FK
  reaching the shard root through its chain. That is the same rule that already decides
  placement, so the two cannot drift.
- **The row cannot be reparented across shard roots**, because a write changing the shard root
  is a delete plus an insert — see [Changing a placement
  key](#changing-a-placement-key).
- **`created_at` and `origin_server` inherit**, because the row cannot outlive its owner.
- **Nothing outside the subtree should reference it.** An outside reference makes the subtree
  non-prunable as a unit, which is worth a warning rather than a prohibition once the delete is
  restricted.

**One bit cannot be derived from the key, and it is lifetime.** Two tables with an identical
key shape want opposite answers:

| Table | Key | On parent delete |
|---|---|---|
| `Order` | `{ customer, order_num }` | orders **survive** — a non-`Component` FK never cascades |
| `OrderLine` | `{ order_ref, product }` | lines **go** — a line has no meaning without its order |

Both are `{ <FK reaching the root>, <local discriminator> }`, and nothing in the key
distinguishes them. `Component` means cascade; its absence means restrict (see [Deleting a
referenced row](#deleting-a-referenced-row)). That is the whole of what it declares.

Two costs to price rather than hide:

- **Ordinal assignment is a per-parent read-modify-write.** It is coordination-free, because the
  parent's shard primary linearizes writes, but it is still a serialization point on that
  parent, where a `DataId` needs none at all. Bounded children — order lines, request headers,
  document nodes — do not notice; a component directly under a shard root with unbounded
  cardinality does. Schema commit prices it with the same diagnostic a table-wide `next` gets
  (see [Sequences](#sequences)), naming the serialization it introduces.
- **`created_at` is the parent's.** The escape is to declare a `Timestamp` field, and it is
  worth deciding at declaration time rather than finding later.

What `Component` buys in exchange is that the ordinal **replaces** the `DataId` rather than
sitting beside it:

| | Ordinary rooted dependent | `Component` |
|---|---|---|
| Surrogate identity | `DataId`, 12 bytes | `Ordinal`, 4 bytes |
| Parent reference | FK column, 12 bytes | the identifier prefix, 0 bytes |
| Declared counter | `order_num : Int = next orderRef`, 4–8 bytes | none needed |

Roughly 24 bytes a row, and that is the whole of the space case. The counter-scoping credit
belongs to the key rule rather than to `Component`: `next <UniqueName>` already allocates within
the named constraint's field list minus the defaulted field, so any rooted key already gets a
shard-local counter with no coordination.

Full treatment of the trait, including the invariants that make the compact identifier sound,
is in [traits.md](traits.md#component).

#### A component default constructs the row

A `DefaultClause` on a component field is a row construction, performed in the same
transaction as the parent's insert:

```
table app.crm.Account : UserData {
  name     : Text unique,
  settings :> Settings : Component = { theme = Dark, digest = Weekly }
}
```

**The target's trait is what makes it a construction rather than a reference**, and that is the
whole difference between the two default shapes a `:>` field admits:

```
created_by :> User = authed_user                      -- references an existing row
settings   :> Settings : Component = { theme = Dark } -- constructs one
```

Because the field is table-valued, `= { theme = Dark }` is **sugar for the one-element table
literal** `= [ { theme = Dark } ]`. Without that reading the default and the field type
disagree. `settings` is a 1:1 component only because the default writes one row; the field
would hold as many as were written.

**A row that must exist whenever its parent exists is a total function of the parent, not an
event.** This is why the "default table" case needs no trigger machinery: `Component` already
owns lifetime and `=` already takes a row construction, so the two compose. No shard question
arises either — a component lives in its parent's row-rooted shard by definition, so the
construction is local.

Both shapes are **insert-time**, and neither may be used on a field added to a table that
already has rows. A construction needs a transaction and an old row has none; `authed_user`
resolves on a read path — to whoever is reading — which would make `created_by` differ between
two readers of the same row. A `:>` field to a `Component` target needs **no `DefaultClause` at
all** when it is added, because its value on an old row is the empty table: inside the declared
type, no write, no ambient input. See [evolution.md](evolution.md#redeclare-a-table) for the
added-column rule and [railroad.md](railroad.md#fields) for the form-by-form list.

Deleting the parent deletes its components, in the same transaction, mechanically over
`Component` edges. There is no cascade declaration and no depth limit to configure, because the
edges *are* the ownership; this is the same statement about lifetime read in the other
direction. Non-`Component` foreign keys never cascade — they restrict, and a delete they block
is rejected (see [Deleting a referenced row](#deleting-a-referenced-row)).

A cross-table in-commit trigger to a **non**-`Component` table is refused. If a row must exist
atomically with another and has independent identity and lifetime, that is a modelling error —
make it a component, or derive it. See
[../events.md](../events.md#internal-effects-are-derived-not-triggered).

## Back-references

`:<` declares a **child table that holds a foreign key back to this one**. It is sugar for
"declare that other table and give it a `:>` back to me": the two produce the same graph, and
`:<` only removes the second statement.

```
table app.pm.Document : UserData {
  title : Text unique,
  :< Comment via document { body : Text, author :> User }
}
```

**The name goes on the right, with `via`, and the parent retains nothing** — no column, no
virtual column, no reverse relation. `via` names the FK field on the child; omitting it defaults
to the parent's table name in `lower_snake_case`. Navigating from the parent to its children is
the ordinary reverse join, where the cost is visible:
`Document >< Comment as c { title, c.body }`. The grammar, the rejected reverse column, and the
`:<`-not-`<:` spelling are in [railroad.md](railroad.md#tables-bindings-traits).

Its scope is children that are **not owned**, because owned 1:many children need no `:<` — a
`:>` to an inline `Component` sub-table is already table-valued. So:

| The child is | Declare it as |
|---|---|
| owned, destroyed with the parent | a `Component` sub-table on a `:>` field |
| independent — its own identity, lifetime, or shard | `:<`, or an ordinary top-level table |

A back-reference and a writable derived table solve adjacent problems and are worth telling
apart. `:<` removes the second *declaration*; a binding over the link table removes the second
*call site*, so the caller never names it
([queries.md](queries.md#writing-through-a-derived-table)). A linking table that callers write
through wants both.

Two consequences follow from `:<` declaring nothing here. `deprecate` addresses the field that
exists — `deprecate app.pm.Comment.document` — rather than a name on a table that does not hold
it. And the child defaults to **this table's replication trait, not `Component`**, because
cascade-by-default is wrong for a construct authors reach for constantly.

## Constraints and access control

Table bodies may contain `assert` blocks alongside field declarations, separated the same
way. Full treatment in [constraints.md](constraints.md):

```
table Order {
  customer  :> Customer,
  bill_addr :> Address,

  assert billingMatch { customer.billing_address == bill_addr },
  assert ownerAccess  { authed_user == customer.user }
}
```
